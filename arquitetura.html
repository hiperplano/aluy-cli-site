architecture

One point decides everything.

The Aluy CLI is one process in your terminal. It reads and edits files, runs commands, and keeps the session, the memory and your key on your machine. Between the model proposing an action and the action happening there is exactly one function — and no path goes around it.

the turn

What happens between enter and the answer.

The !command you type at the prompt is not a shortcut: it builds the same tool proposal and goes through the same decision. Same for subagents, for hooks and for /init.

the gate

What it lets through, and what it stops.

The base rule is to deny. What gets through is written in code, not in the prompt — so there is no text that talks the model past it.

allow

goes straight through

Only what reads and changes nothing: read file, grep, glob and list. Plus writing a memory and speaking in a room.

ask

always asks

Running a command, editing and writing a file. And any tool it does not know — including every tool that comes from an MCP server.

deny

denies, does not ask

Reading ~/.ssh, ~/.aws, ~/.gnupg, private keys and certificates. And its own ~/.aluy/ folder — it may neither read it nor write to it.

And the exception, in full: --yolo returns allow before any of this. Under it the agent reaches its own ~/.aluy/ folder — the MCP config, the hooks, the undo journal and the credential vault. That is a deliberate decision of the mode, not a hole. Everywhere else, that rule holds.

Five command categories cannot be relaxed, not even by editing the config: destructive commands, network commands, privilege escalation, package installs, and writing to a startup file. Every tool from an MCP server is its own locked category. The /permissions panel can only touch two read tools — the rest shows up locked.

the modules

Two halves, with a border the build enforces.

Three things the drawing cannot carry: the connection to your provider is pinned to the IP it resolved and refuses redirects; the destination of a Telegram message is not an argument of the model, so an injected instruction cannot send anything elsewhere; and the version check installs the update by itself until you turn it off with ALUY_AUTO_UPDATE=0.

the state

Where each thing lives.

All under ~/.aluy/, readable only by your own user account — no other account on the machine gets in. There is no database anywhere: the memory index is a Markdown file you can open and edit.

sessions/

session and transcript

One JSON per session, with the blocks of the conversation and what you ran.

undo/

undo journal

The previous state of each file, encrypted. The key belongs to the session and dies with the process — undo does not survive a restart.

memory/

memory

Markdown: one global, one per project. One fact per line, editable by hand.

keyring

credential

In the OS vault, or an encrypted file where there is none — with the key derived from the machine, never written down.

config.json

configuration

Theme, model, backend, profile, services. Plus the hooks and the MCP servers, each in its own file.

agents/ skills/

what you write

Agents, commands, skills, workflows and plugins: .md files you can put in version control.
